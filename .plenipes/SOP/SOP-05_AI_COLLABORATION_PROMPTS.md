# SOP-05: AI Collaboration & Sovereignty Prompts
# AI 协作与代码主权提示词规范

> **Status:** MANDATORY (强制执行)
> **Target:** All AI Assistant Interactions
> **Version:** 1.0.0 (2026-05-14)

为了确保 Illacme Plenipes 项目在长期迭代中的稳定性，AI 助手在执行任务时必须根据任务类型激活对应的“主权防御模板”。

---

## 模板一：【深度重构/模块拆分】
**Identifier:** `[ACTIVATE: DEEP_REFACTOR_SOVEREIGNTY]`
**适用场景：** 文件拆分、架构重组、核心逻辑改写。

1. **物理克隆原则 (Genome Cloning):** 严禁进行任何未授权的逻辑修剪、压缩或“优化”。
2. **注释封印 (Docstring Sovereignty):** 必须 100% 迁移并保留所有原始 docstrings、行内注释和 TODO。
3. **完整性约束:** 严禁使用省略号或“代码保持原样”占位符，必须输出闭环的可执行代码。
4. **变更清单:** 在执行写入前，必须先列出所有即将被删除的代码段及其对应的迁移目的地。

### 示例指令
> “请按照【模板一】将 `plenipes.py` 中的核心循环逻辑拆分到新的 `core/engine/loop.py` 中。记住，禁止优化代码，必须 100% 保留原有注释和异常处理逻辑。”

---

## 模板二：【API/适配器联调】
**Identifier:** `[ACTIVATE: ADAPTER_CONTRACT_PROTECTION]`
**适用场景：** 修改底层适配器（Compute/Ingress）、调整 Base 类接口。

1. **证据优先 (Evidence First):** 必须先读取当前接口的 Schema 或前端调用逻辑。
2. **契约锁死 (Contract Lock):** 严禁修改任何现有的 API 返回字段名和层级结构。
3. **隐性依赖审计:** 全局搜索引用该接口的所有模块，确保解耦激活逻辑不会失效。
4. **零破坏回归:** 必须书面证明修改后的响应结构与旧版实现物理兼容。

### 示例指令
> “使用【模板二】更新 `adapters/compute/deepseek.py`，增加对流式 API 的支持。在修改前，请先对比 `base.py` 的接口定义，确保返回字段名完全一致，不要修改前端正在使用的 `usage` 字段结构。”

---

## 模板三：【UI/UX 样式调整】
**Identifier:** `[ACTIVATE: INDUSTRIAL_AESTHETIC_AUDIT]`
**适用场景：** CSS 修改、前端组件更新、看板交互调整。

1. **像素级审计 (Visual Parity):** 必须保持与现有工业级组件的视觉对齐。
2. **规范约束:** 必须使用已定义的 CSS Tokens，严禁使用硬编码色值。
3. **响应式锁定:** 修改不得破坏现有侧边栏或网格布局在不同视口下的逻辑。
4. **动效保护:** 禁止移除现有的微交互动画，保持“流畅且高级”的感官标准。

### 示例指令
> “按照【模板三】优化 `governance.css` 中的按钮样式。必须使用项目既有的 HSL 变量，确保在深色模式下与侧边栏的边框色保持像素级对齐，严禁删改已有的 hover 动画逻辑。”

---

## 模板四：【系统重启/治理对齐】
**Identifier:** `[ACTIVATE: CONSTITUTION_ALIGNMENT]`
**适用场景：** 修复启动报错、AI 表现异常、环境安全探测。

1. **宪法校验 (Constitution Audit):** 立即重新审阅 `SOP_MASTER_CONSTITUTION.md`。
2. **主权重置:** 停止当前生成，对比需求与项目“工业级稳定性”要求的冲突。
3. **安全沙箱:** 运行破坏性 shell 指令前，必须先进行非破坏性环境探测。
4. **决策溯源:** 解释 Bug 产生原因及其对架构可持续性的影响。

### 示例指令
> “系统启动报错 `ImportError`，请激活【模板四】进行诊断。在修复前，先对照 `SOP_MASTER_CONSTITUTION.md` 检查是否因为之前的重构破坏了路径依赖，并在修复后说明该问题对治理体系的潜在风险。”

---

## 模板五：【工程化测试与验证】
**Identifier:** `[ACTIVATE: ENGINEERING_VALIDATION_FLOW]`
**适用场景：** 提交代码前的单元测试、集成测试、UI 自动化验证。

1. **先探测后验证:** 必须先列出项目中现有的测试框架和测试路径。
2. **零容忍回归:** 修改后必须运行相关单元测试，并展示 `PASS` 状态。
3. **环境复现:** 严禁仅凭直觉判断修复，必须在可能的情况下编写一段临时脚本（scratch script）验证逻辑。
4. **日志审计:** 在报告中展示关键路径的 debug 日志，证明执行流符合预期。

### 示例指令
> “我修改了 `core/ingress/manager.py`，请使用【模板五】进行验证。你需要先找到现有的适配器测试用例并运行，如果测试覆盖不足，请编写一个 scratch 脚本模拟 10 种不同的输入源来确保逻辑严密。”

## 模板六：【环境探测与依赖梳理】
**Identifier:** `[ACTIVATE: ECOSYSTEM_AWARENESS]`
**适用场景：** 安装新包、使用 shell 指令、分析底层依赖。

1. **非破坏性探测:** 禁止直接运行安装/删除指令。必须先运行 `pip list`、`npm list` 或 `ls` 确认环境现状。
2. **依赖冲突检查:** 分析新引入的包是否与现有 `requirements.txt` 或 `package.json` 冲突。
3. **副作用评估:** 必须说明该环境变更对其他团队成员或部署脚本的影响。
4. **回滚预案:** 在执行环境变更前，说明如果失败将如何恢复。

### 示例指令
> “我们需要引入 `pydantic` 来做数据校验，请激活【模板六】。先检查当前环境已安装的包，评估引入 pydantic 对现有适配器的潜在影响，并列出修改 `requirements.txt` 的安全步骤。”

## 模板七：【多文件协同修改】
**Identifier:** `[ACTIVATE: MULTI_FILE_SYNC_ATOMIC]`
**适用场景：** 跨模块的功能开发（如：增加一个字段，需要同时改适配器、看板和 CSS）。

1. **原子性提交:** 必须在同一个 `Implementation Plan` 中列出所有关联文件。
2. **依赖排序:** 必须按照“依赖项 -> 调用者 -> 表现层”的逻辑顺序执行修改。
3. **全链路搜索:** 必须搜索项目中所有相关的 `registry` 或 `factory` 确保入口已同步。
4. **断层检查:** 在最后一步，检查是否存在修改了接口但未修改前端调用的“悬空”逻辑。

### 示例指令
> “使用【模板七】在整个系统中添加‘多模态输入’支持。你需要同时修改 `core/ingress/base.py`、`adapters/compute/` 下的所有模型适配器，以及前端看板的上传组件。请严格按照依赖顺序执行，确保不出现调用断层。”

## 模板八：【文档与注释同步】
**Identifier:** `[ACTIVATE: KNOWLEDGE_SYNC_MANDATORY]`
**适用场景：** 完成功能后同步 README、SOP 或代码中的 ADR（架构决策记录）。

1. **README 同步:** 代码逻辑变更后，必须同步检查并更新相关的 `README.md` 或文档说明。
2. **ADR 记录:** 凡涉及重大设计变更，必须在 `.plenipes/history/` 中记录决策理由。
3. **示例更新:** 如果修改了 API，必须更新代码示例或测试用例中的 Mock 数据。
4. **版本标记:** 确保代码注释中的 `@version` 或 `@last_modified` 已更新。

### 示例指令
> “任务完成，请使用【模板八】进行知识同步。更新主目录的 `README.md`，并在 `.plenipes/history/` 中记录本次重构中关于‘解耦 publisher’的架构决策理由，同时确保所有受影响文件的注释版本号已更正。”

---

## 模板九：【业务严谨性与逻辑闭环】
**Identifier:** `[ACTIVATE: LOGICAL_CLOSURE_DEFENSE]`
**适用场景：** 表单提交、交互操作设计、关键业务流程实现。

1. **全边界扫描 (Edge Case Scanning):** 在编码前，必须先列出至少 5 个可能导致业务失败或非法的输入/状态组合。
2. **三层校验拦截:**
   - **输入层:** 实时正则、类型检查及长度校验。
   - **业务层:** 跨字段联动逻辑校验（如 A 选则后 B 必须有值）。
   - **防护层:** 提交按钮的防抖（Debounce）/禁用（Disabled）及 Loading 状态管理。
3. **视觉反馈闭环:** 所有的校验拦截必须配套对应的 UI 提示（Error/Toast），严禁静默失败。
4. **异常逃逸禁止:** 禁止使用空的 catch 块，必须对所有 API 调用失败进行明确的降级处理或错误上报。

### 示例指令
> “请按照【模板九】为 Compute 配置面板添加‘模型切换’逻辑。要求：必须校验当前 API Key 是否有效，切换时需有 Loading 遮罩，且如果模型参数未保存，必须弹出联动确认框拦截用户的退出行为。”

---

## 模板十：【视觉主权与布局稳健性】
**Identifier:** `[ACTIVATE: VISUAL_STEADFAST_LAYOUT]`
**适用场景：** 页面重构、响应式调整、新组件开发、视觉效果优化。

1. **容器边界自省 (Box Model Audit):** 修改前必须通过 `browser_subagent` 或阅读 CSS 明确目标元素的盒模型约束。
2. **防御性 CSS 策略:** 
   - 必须处理 `overflow` 溢出。
   - 必须处理 `flex-wrap` 或 `grid` 的自适应对齐。
   - 必须处理长文本截断（Ellipsis）。
3. **4px/8px 工业网格系统:** 严禁使用非步进像素值。
4. **SOP-03 审美对齐:** 所有的色彩、模糊度、阴影及动效曲线必须严格引用 `SOP-03 Section 3`。

### 示例指令
> “激活【模板十】重构 `Compute Center` 的模型列表页。要求：必须遵循 SOP-03 的 8px 网格规范，使用玻璃拟态材质，并确保在移动端 375px 下列表能够自动折叠为单列布局而不会产生错位。”

### 组合实战场景 (Composite Scenarios)

当面对复杂任务时，建议组合使用模板以达到最大防御力：

1. **全生命周期开发流 (开发 + 验证 + 知识沉淀)**
   > “使用**【模板七】**在项目中接入一个新的 Ingress 源，完成后激活**【模板五】**编写 scratch 脚本验证接入逻辑，最后通过**【模板八】**同步更新项目文档。”

2. **生产环境紧急修复 (诊断 + 契约保护)**
   > “系统当前无法连接到 ZhipuAI，请启动**【模板四】**进行故障诊断，确认问题后按照**【模板二】**的要求修复适配器，严禁修改任何现有的输出 Schema。”

3. **核心架构演进 (重构 + 多文件同步)**
   > “请激活**【模板一】**对 `core/editorial/` 进行物理克隆式的模块化拆分，并配合**【模板七】**同步更新所有受影响的 Registry 文件，确保全链路调用无断层。”

4. **高阶 UI 交互升级 (审美硬指标 + 逻辑闭环防御)**
   > “使用**【模板十】**对 Compute 看板的设置面板进行视觉重构，必须符合 SOP-03 的玻璃拟态标准。同时叠加**【模板九】**，为表单添加输入校验和提交防抖，确保视觉和业务逻辑双重稳健。”

5. **底层依赖安全迁移 (环境探测 + 物理克隆 + 验证)**
   > “启动**【模板六】**探测当前 Python 依赖环境，随后使用**【模板一】**将原有的解析器迁移至新版本，最后激活**【模板五】**运行全量回归测试，确保迁移过程不丢失任何原始注释和逻辑分支。”

6. **工业级 API 物理对齐 (契约保护 + 多端巡检 + 文档同步)**
   > “按照**【模板二】**更新 `openrouter.py` 适配器，确保 API Schema 100% 对齐。随后激活**【模板十】**检查前端看板在数据更新后的渲染稳定性，最后通过**【模板八】**同步更新 ADR 架构决策记录。”
